## Next actions (ordered) — the todo list

The sequenced view of open work. Each item links to the thematic detail below. Order encodes dependency: an item should not start before the ones above it land.

**Foundations first.** The build-time *structure* — property-agnostic, compiled at deploy — is the ground everything else binds to, so it is built before any runtime/engine work. There are **two** build-time foundations: the **buyer fact base** (#1–2, done/reconciled) and the **property model** (#3, not yet built deliberately). The structure/data line is the discipline: a `scope: per-property` component's *structure* is built now even though it *executes* only when specific property data arrives via the narrow Phase-B paths — so deferring *structure* to a data-trigger (Phase B / F9) is a category error. The compiler (#4) is the *instrument* that materializes + validates both foundations; it does not emit a usable artifact until the structure it validates is complete.

## The core gap (why this doc exists)

There is **no materialized foundation** to reason against. The canonical fact model — the *resolver-input registry*, the typed surface every KB rule binds to — exists only as prose in [`architecture/architecture.md`](architecture/architecture.md) §11.9 ("the union of upstream `outcome_schema` fields"). It has never been computed into an artifact. Each of the four blueprints declares its own facts independently (`citizenship_status` vs `visa_class`, `firb_required` vs `firb_required_any`); KB rules bind to field-name *strings*; nothing ties them together except a human reconstructing the whole picture in their head. That reconstruction kept being wrong — hence issue-after-issue.

The fix is two-sided:
- **Structural** — materialize the registry as an artifact (the compiler's output *is* this); make it the thing reasoning binds to instead of memory.
- **Behavioural** — verify against the live source (the actual file, re-read) *before* asserting. See Working discipline below.
